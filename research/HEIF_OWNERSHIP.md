# Native capture HEIF completion and output ownership

The downloaded A7C II 2.01 `av-cam.bin` contains a direct native capture HEIF route to the MC still encoder. After a successful encode, the capture stage releases its input, records the output handle in capture state, and detaches that output from its local cleanup tracker. Successful publication of still information can then invalidate the capture state's saved output handles. This establishes a concrete transfer boundary; it does not establish the eventual receiver-side resource free or a working LUT-to-HEIF route.

Evidence is [heif-ownership.json](evidence/heif-ownership.json), generated by [trace_heif_ownership.py](trace_heif_ownership.py). This is **original instruction evidence plus isolated host execution, not REA Evidence**. The source is `research/extracted/ILCE-7CM2-2.01/firmware.tar_unpacked/0700_part_image/dev/nflasha3_unpacked/av-cam.bin`, 13,797,088 bytes, SHA-256 `90343f5f2edc0393ad8809d907cfe648dfd3a82ce0ef39cf06167929d8955096`. All addresses below are **file offsets**; the evidence also records the supported offline linked address `0xffffffc001000000 + offset`. That mapping is not a measured camera address.

## Capture submission reaches the native MC protocol

The main capture stage at `0x1ff7b0` constructs a local tracker (`0x207204`), calls Prepare (`0x1ffb9c`), Exec (**`0x1ffee0`**), Wait (`0x200268`) and, only on successful preparation/submission/completion, Post (`0x2002f4`). It destroys the tracker at `0x1ffa10`, with another destructor call on its exception tail. `0x1ffedc` is Prepare's return instruction, not the Exec entry.

Exec calls the capture resource method `0x1f8f28` at `0x200214`. This differs from the separately traced JPEG wrapper/callback route. The resource method obtains a reply identifier through `0x1f91bc` → imported service `0x2f078(0x2a, 5, outID)`, constructs an 88-byte frame body, and calls `0x1f9210`. The latter copies the body into a 96-byte message with four little-endian halfwords `{0x2003, 0x010e, 0x0060, 1}` and sends it to `0x8057060a` through `0x97058`.

The full original body producer, reply-ID wrapper and envelope sender execute together in 96 host fixtures covering the three accepted modes, four quality selectors and every combination of three binary flags. Actual codec execution is replaced by a recording transport stub. Selected body fields observed in these fixtures are:

| Body offset | Original writer / observed content |
| --- | --- |
| `+0x00` | 64-bit session value from resource object `+0x1b8` |
| `+0x08` | channel, zero extended to 64 bits |
| `+0x10` | 32-bit allocated reply identifier |
| `+0x14` | 32-bit mode, accepted range 0–2 |
| `+0x18` | 32-bit selector, caller value 0–3 plus `0x100` |
| `+0x1c..1e` | flag mapping `{2,0}` and two zero bytes |
| `+0x20` | input resource value supplied in `w7` |
| `+0x28` | 64-bit input address argument |
| `+0x30..33` | `0x0100` halfword, byte `{0x57,0x58}`, byte `{1,0}` |
| `+0x34,+0x36` | first two 16-bit geometry arguments |
| `+0x38..43` | twelve zero bytes |
| `+0x44,+0x46` | second two 16-bit geometry arguments |
| `+0x48,+0x50` | 64-bit output address and length argument |

This table deliberately leaves padding bytes `+0x1f` and `+0x24..27` uninterpreted. These tests check original writes to defined fields; they do not claim an independently standardized pixel format or meaningful padding content. Flag meanings and geometry semantics require their caller context, not these fixture values alone.

The category/selector/destination match the original receiver and completion builder independently retained in [HEIF_BINDING.md](HEIF_BINDING.md): `0x1a7e2c` routes `0x010e` to `0x1ab124`, and `0x1a8470` constructs the `0x810e` completion. Therefore the missing `532/533/534` entries in the **separate AP shared library's** local conversion table are not evidence that this native capture route is blocked. These bytes still do not prove that either route executes successfully on the camera.

## Completion supplies the recorded area length

Wait `0x200268` selects the per-slot resource pointer from capture context `+0x858` and channel from `+0x868`, then calls `0x1f931c` with the reply ID and a 32-bit output-length pointer. `0x1f931c` clears that length first, validates the channel, and calls `0x1f9454`.

The latter constructs a message receiver, calls `0x9681c` with the reply ID and timeout `0xffffffff`, and obtains source metadata through `0x94bd0`. A source other than `0x8057060a` is logged and retried. A matching source permits a 32-byte message copy through `0x94978`; it extracts 64-bit values at message `+8`, `+0x10`, and `+0x18` into a local response. The higher parser checks the **32-bit status at message `+0x10`** and, when zero, stores the **low 32 bits of the 64-bit ES size at `+0x18`** into the caller's output-length location. Its return packs success in the low bit and error status in the high 32 bits.

Twenty-four host cases cover validation failure, zero/nonzero MC status, a wrong-source message followed by the expected source, and lengths including `0x100000005 → 5`. That last fixture proves the narrowing operation, not that a camera would accept a 4 GiB output. Synthetic completion messages use `{0x2003,0x810e,32,1}`; this receive body visibly filters the transport source, while its shown extraction does not validate those header halfwords. Receive-service failure, queue cancellation, actual transport ordering and codec timeouts remain outside the tested cases.

## Post transfers the output out of local cleanup

Post `0x2002f4` receives the input descriptor, output descriptor, local tracker, capture context and completed 32-bit codec length. It writes four-word resource areas using the real routing/update functions:

| Mode | Area offset within still-info accumulator `ctx+0x440` | Saved output handle in capture context |
| --- | --- | --- |
| 0 | `+0x144` for slot `1`; `+0x2a4` for slot `0x10` | `+0x424 + 24*slotIndex` |
| 1 | `+0x164` and/or `+0x2c4` for entries whose type is `4` | `+0x364` |
| 2 | `+0x154` and/or `+0x2b4` for entries whose type is `4` | `+0x368` |

The four stored words are `{outputHandle, 0, completedCodecLength, outputUnitType}`. The real `0x1f484c`, `0x1f4888`, `0x1f490c` routers and `0x1f435c` updater execute in the fixtures. These are the same area records later copied by the still-info producer. The mode labels here remain numeric; this report does not assign screen/thumbnail semantics merely from their ordering.

For mode 0, the real resolver `0x1f4a84` calculates grid/object pointers from the selected still-info entry plus context `+0x7e8`. Post uses the pointer at its result `+8` for calls to `0x1f2890` and `0x1f2934`, passing a selector derived from context `+0x7ac` and the info word `+4`. It also records diagnostics through `0x1f29b4` and the 64-bit output address through `0x1f2d68`. The tests retain those call arguments but stub these metadata operations: they do not reconstruct a valid grid object or prove grid geometry/HEVC tile layout.

Common cleanup calls original wrapper `0x208c5c(inputHandle, 2, 0x0061003c)`, which invokes resource operation `0x20bc30(inputHandle, 2, 5, tag)`. On return zero, Post invalidates the consumed input handle in context (`+0x41c + 24*slotIndex`, `+0x33c`, or `+0x340`). It stores the output handle regardless of that release result and calls `0x2075f8(tracker, outputHandle)`. This helper finds the tracker entry and writes handle `0xffffffff` and release-mode halfword zero. The destructor at `0x207240` skips invalid entries and releases other registered handles through the same wrapper, using each entry's mode halfword.

Twenty-four Post cases cover all three modes, both slots, both debug branches, and successful/failed input release. Original Post followed by the original tracker destructor releases the synthetic input and an unrelated temporary, while **the detached output is not released**. Failed input release retains its old context handle but still detaches/stores the output; that observation alone is not a demonstrated bug. Two additional cases omit Post and show that the destructor releases a still-owned output. All resource-operation calls are intercepted; no physical memory allocator or codec runs.

## Publication and codec close are separate lifetime boundaries

The real still-info producer `0x203510` copies accumulator `0x364` bytes to a message at `+0x14`, sets kind `4`/tag `0x1006`, and sends to `0x80020002`. After a successful send, **context `+0x84` bit 2** selects HEIF-handle invalidation. It clears context `+0x364/+0x368`, then clears `+0x424` and/or `+0x43c` according to the slot bits returned by `0x1f40e8`. A send failure returns before this clearing and frees the message object. Twelve host fixtures verify these branches and prove that the published area bytes retain the handles/length while context ownership markers change. Clearing a local handle is not itself an allocator free, nor proof of receiver-side retention.

`Stage_ReleaseHif` at `0x1fee18` selects the codec resource from `ctx+0x858`, calls `0x1f78c0(resource,channel)`, and clears that resource pointer/channel. Eight host cases cover both indices, absent/present resources and success/error packed close results. This stage leaves the tested saved output handles `ctx+0x364/+0x368` unchanged. Its name does not establish output-buffer release. Eventual receiver-side sharing/freeing and its relationship to recording completion need separate evidence.

## Reproduction and limits

```sh
.venv-research/bin/python research/trace_heif_ownership.py
.venv-research/bin/python -m py_compile research/trace_heif_ownership.py
```

Result: **168 host cases pass; 17 source ranges retain 1,747 exact original instructions**. The generator pins the original source SHA, itself and its shared raw-machine helper. No ignored generated payload is required to read this evidence.

The harness maps the raw image into a bounded host emulator arena. Logging, channel validation, reply-ID allocation, IPC/message operations, grid metadata calls, resource operations and codec close are explicit stubs; all data, addresses, statuses and codec lengths are invented fixtures. No firmware image changes, target execution, camera communication or codec work occurs. This reconstructs output lifetime and a native command route, while pixel content, cache/coherency, final buffer reclamation, actual HEVC validity and any LUT insertion point remain unproved.
